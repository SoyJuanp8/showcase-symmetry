# Database Schema (Firestore) - Symmetry App

## 1. Introduction
This document defines the NoSQL database schema (Cloud Firestore) for the 'Journalist' functionality and the news feed of the application. The design follows the **Clean Architecture** principles outlined in `APP_ARCHITECTURE.md` and is optimized for scalability and frontend performance.

## 2. Collection: `articles`
This collection stores all news articles created by the journalists (users). Each document in this collection represents a single article.

### Document Structure

| Field | Type | Description | Example |
| :--- | :--- | :--- | :--- |
| `id` | String | Unique document identifier (auto-generated by Firestore). | `8f2nL3b...` |
| `firebaseId` | String | Redundant storage of the ID for domain mapping. | `8f2nL3b...` |
| `title` | String | Main headline of the article. Must be concise and descriptive. | "Generative AI Advances" |
| `content` | String | Full body of the article. | "### Subtitle\n\nContent..." |
| `description` | String | A brief summary or snippet for the feed/preview cards. | "An overview of..." |
| `urlToImage` | String | Public URL of the cover image in Cloud Storage. | `https://firebasestorage...` |
| `url` | String | External URL of the original article (optional). | `https://example.com/news` |
| `publishedAt` | String | Publication date/time in ISO 8601. Key for sorting. | `2025-12-06T14:30:00Z` |
| `author` | String | Display name of the author. | "Jane Doe" |
| `userId` | String | Firebase Auth UID of the creator options (Ownership). | `uid123` |
| `likes` | Array<String> | List of User IDs who have liked the article. | `["user1", "user2"]` |
| `comments` | Array<Map> | Embedded list of comments. | `[{ "text": "...", "author": "..." }]` |

## 3. Design Decisions
The following decisions were made to ensure a robust, scalable schema aligned with Firestore best practices and Symmetry guidelines.

### 3.1. NoSQL Model & Denormalization
*   **Embedded Engagement (`likes`, `comments`)**: Engagement data is embedded directly within the article document. This denormalization strategy avoids the need for extra sub-collection queries ("joins") when loading the feed, reducing latency and read costs.
*   **Flat Author (`author`)**: Unlike complex relational models, we store the author's name as a flat string. This ensures the article retains the historical author name even if the user updates their profile later, and simplifies the data layer.

### 3.2. Optimization for 'Lazy Loading' & Infinite Feed
*   **Field `publishedAt`**: This field is fundamental for implementing an efficient infinite news feed.
*   **Pagination Strategy**: The frontend performs paginated queries ordering the articles descending by `publishedAt`. To load more articles, the client uses the `publishedAt` of the last visible article as the cursor (`startAfter`) for the next query.

### 3.3. Media Separation (Cloud Storage)
*   **Field `urlToImage`**: Heavy images and binary files are **not** stored in Firestore to avoid exceeding the 1 MiB document limit and to keep costs low. Instead, they are uploaded to Firebase Cloud Storage, and only the public access URL is stored in the `urlToImage` field.

### 3.4. Alignment with Clean Architecture
*   This schema defines the structure of the `ArticleModel` in the **Data Layer** of our architecture.
*   The `ArticleModel` extends the `ArticleEntity` defined in the **Domain Layer**, which contains only pure business logic without any dependencies on Firestore.
*   The `ArticleRepositoryImpl` (Data Layer) is responsible for mapping Firestore documents to `ArticleModel` instances.
